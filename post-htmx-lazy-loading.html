给静态博客做按需加载

2026-10-09咖啡笔记JavaScript · htmx

首页脚本从 102.7 KB 降到 57.4 KB，以及快速切页时需要处理的两件事。

这次整理博客时，发现首页会一起加载 IP 检测代码和地址解析库，尽管首页根本没有检测工具。把这部分依赖推迟到进入文章时加载后，首页的项目脚本体积减少了约 44%。改动里更值得记下的，是另一个时序问题：模块还没加载好，读者已经离开了那篇文章。

下面以这个站点的实际实现为例，记录从依赖拆分到页面卸载的完整过程。代码对应 navigation.js 和 ip-check.js，使用 htmx 2.0.11。

这篇记录的四个步骤

  1. 先看首页到底加载了什么
  2. 把检测工具变成按需加载的模块
  3. 处理快速切页和请求清理
  4. 把容易漏掉的时序写进验证

先看首页到底加载了什么

改动前，每个页面都引用四个脚本：htmx、导航逻辑、IP 检测逻辑和 ipaddr.js。它们都加了 defer，但 defer 只是调整执行时机，浏览器仍然会下载这些文件。要减少首页的依赖，需要把检测工具从公共入口里移出去。

把检测工具变成按需加载的模块

这个博客用 htmx 更新中间正文，页头、导航和页脚一直保留。新页面的 #page-content > main 替换进来后，由 navigation.js 检查正文里有没有 .ip-tool。只有找到工具，才调用动态 import()。

ip-check.js 导出 mountIPCheck(tool)，负责启动当前文章里的检测，并返回一个清理函数。地址解析继续使用已有的 ipaddr.js。原始依赖是面向 CommonJS / 普通脚本的包装，因此用 esbuild 生成浏览器可导入的 ES 模块，产物随站点一起提供。

生成的 ipaddr.mjs 为 12,943 字节，版本、命令和校验值记录在 vendor/ipaddr.js/SOURCE.json。IP 文章本身还有一条 modulepreload，让直接访问这篇文章时可以提前获取工具模块；普通页面没有这条预加载。

这里要区分两件事：同一文档中，成功加载的同一模块可以复用；每次切页得到的 DOM 却是新的。再次进入 IP 文章时，仍要对新的工具节点调用 mountIPCheck()，不能把上一次的页面实例一并复用。

处理快速切页和请求清理

假设读者打开 IP 文章，又马上点了“关于”。如果只在 await import() 后初始化工具，模块稍后加载成功时，就可能给已经离开页面的节点启动一组检测。为此，导航层保留一个递增的 mountVersion。

新一轮装载先卸载上一轮，再记住当前版本。等模块返回时，版本仍一致，才允许初始化。下面节选同一次 mount() 调用中与这个判断有关的代码；完整函数还负责导航高亮、焦点和错误提示。

这解决了“等待模块时离开”的情况。版本检查会阻止过期初始化，但不会取消模块本身的下载。 另一种情况是工具已经启动，IPv4、IPv6 或网站出口的请求还在路上，此时需要清理工具自己的工作。

返回的清理函数负责标记失效、中止请求和移除刷新按钮的监听器。异步结果回写界面之前也会检查 disposed，防止已经卸载的实例继续更新状态。

这些动作接在 htmx 的页面生命周期上：新正文通过检查、即将替换时卸载旧工具；htmx:afterSwap 后装载新工具；htmx:historyRestore 后重新装载并恢复滚动位置。只有请求开始、页面还没替换时，旧工具继续留在原页面上。

模块加载失败也要收尾。当前实现会显示加载错误，停止“准备检测”的状态，并提供“重新加载页面”按钮。错误分支同样检查版本，过期页面的加载失败不会覆盖新页面。刷新由读者点击触发。

把容易漏掉的时序写进验证

手动慢慢点击，很难碰到前面的竞态。现有 Playwright 回归会暂时扣住模块响应或 IP 响应，等页面切走后再观察结果。这次记录对应的 12 项回归全部通过，其中与按需加载直接相关的检查包括：

  • 直接访问首页、文章列表和关于页，不加载 IP 模块，也不请求检测接口。
  • 两次进入 IP 文章，模块只请求一次，每次都给当前正文重新初始化工具。
  • 模块还没返回就离开，等它加载完成后，也不会启动旧页面的检测。
  • IPv4 请求未完成时离开，请求被中止，依赖它的归属地查询不会继续发出。
  • 模块请求失败后有明确提示，解除失败条件并手动重载，可以恢复检测。

以后再加工具时

这次留下一个明确的分工：导航层决定哪一轮页面还能装载，具体工具负责自己的请求和事件监听。模块可以缓存，每轮页面实例都要有自己的初始化与清理。下一次增加异步工具时，先把这两个边界接好，再去测实际节省了多少资源。
